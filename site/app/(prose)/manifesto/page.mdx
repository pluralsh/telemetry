## Rethinking observability for the agentic era

In my years operating large cloud infrastructure, the most common pain point was the observability bill. The choice usually came down to:

1. the heavy operational toil of running a telemetry stack that absorbs very high write throughput, or
2. a very large Datadog bill to have someone else run it.

Almost everyone picked the second option, because Datadog does the hard part well and builds a great product on top. We think that world has changed, for two reasons:

* Agents are becoming the primary consumers of observability data, and all they need is a programmable REST API. The real value is in the data layer.
* Observability data is a natural fit for the new generation of object-storage-native databases built on LSM trees, which makes the old operational toil far more manageable.

We're investing in both. [Plural](https://plural.sh) provides a full agentic platform engineering solution, with observability as a core integration point. Plural Telemetry, meanwhile, pushes [SlateDB](https://slatedb.io/) as far as it will go to build an operationally simple observability toolkit on plain Kubernetes and object storage.

The goal: high-quality, fast telemetry from three YAML files, an S3 bucket and a small AWS bill.

## Key design principles

### 1. Object storage is the database

S3 provides effectively unlimited durable storage, and SlateDB tiers hot data into local NVMe caches. That allows a simple reader/writer architecture that scales without limit.

### 2. Fewer moving parts

Existing solutions all have operational warts. The LGTM stack has a complex microservices architecture, needs external caching in memcached, and suffers from poor tail latencies. VictoriaMetrics still requires you to manage durable storage yourself, on top of its own sharding complexity.

Plural Telemetry is simple: scale sharded writers to match ingest, and scale readers to match queries. Everything else is synchronized through a single S3 bucket.

### 3. Compatible by default

Re-instrumenting is a non-starter. Each database speaks the protocols you already run: Prometheus remote write, Loki push, OTLP, Zipkin, Elasticsearch `_bulk`. Each answers PromQL, LogQL or TraceQL through the same HTTP APIs Grafana already uses. Switching should be a change of URL.

### 4. Kubernetes is the control plane

Distributed databases usually bring their own consensus system. Kubernetes already *is* one, and it's already running. Plural Telemetry coordinates through StatefulSets for stable identity, a `ShardMap` custom resource for routing, and `Lease` objects for shard ownership, so there's no ZooKeeper, etcd or gossip protocol to operate.

### 5. Scale without moving data

Rebalancing is where distributed stores get dangerous. Because telemetry is ordered by time, Plural Telemetry scales by changing where *future* data goes. A new routing epoch takes effect at the next hour boundary, new shards start empty, and nothing is copied. See [epoch sharding](/sharding/).

### 6. Prove it

Claims about speed and compatibility are cheap. Every database is fuzzed against its reference implementation on identical data, and the latency, CPU and memory of both sides are recorded and published, including the cases where we lose. See each database's **Benchmarks** page.

### 7. Open, and sponsored by Plural

Plural Telemetry is AGPL v3 and developed in the open by [Plural](https://plural.sh), with Plural-built images under MIT and the operator and Helm charts under Apache 2.0 (see the [LICENSE](https://github.com/pluralsh/telemetry/blob/main/LICENSE)). Plural runs fleets of Kubernetes clusters for its customers, and cheap, boring observability is a prerequisite for doing that well.

## What we won't do

- Build a proprietary query language. If PromQL, LogQL and TraceQL can express it, that's what we implement.
- Require a managed service. Everything runs in your cluster, against your bucket.
- Hide the trade-offs. Writer shards aren't replicated in-cluster: failover moves a `Lease` and reopens the same data from object storage. Scale-down isn't supported yet. Both are documented, not glossed over.
