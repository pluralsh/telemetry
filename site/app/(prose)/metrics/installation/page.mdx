This guide assumes the operator is already installed; see [Installation](/installation/). Examples use the `telemetry` Kubernetes namespace and an S3 bucket named `acme-telemetry`.

## Choose a mode

| Mode | Pods | Storage | Use it for |
| --- | --- | --- | --- |
| [Standalone](/metrics/installation/standalone/) | One pod that ingests and queries | A volume, or a bucket | Development and small clusters |
| [Reader/writer split](/metrics/installation/read-write/) | One writer, autoscaled readers | A shared bucket | Heavy query load on modest ingest |
| [Sharded](/metrics/installation/sharded/) | Several writers, a reader group per shard | A shared bucket | Ingest beyond one writer |

The split and sharded modes are the same `Sharded` resource with one writer or several, so a split deployment grows into a sharded one by raising `spec.writer.replicas`.

## Grant S3 access

Skip this for a standalone database on a volume. Otherwise Metrics authenticates to S3 with [EKS Pod Identity](https://docs.aws.amazon.com/eks/latest/userguide/pod-identities.html). The operator creates a ServiceAccount named after the database, `metrics`, so associate an IAM role with it:

<PodIdentitySetup product="metrics" />

The role's trust policy must allow `pods.eks.amazonaws.com` to call `sts:AssumeRole` and `sts:TagSession`. No keys go in the spec.

## Access

Metrics serves a tenant namespace only once it has credentials. Each `NamespaceAuthentication` creates its namespace if needed and grants one username `read` or `write`. Create the password Secrets first:

<PasswordSecrets product="metrics" />

Then grant a writer for the collector and a reader for Grafana:

<AccessSpec product="metrics" />

Clients send these as HTTP basic auth.

<Callout title="Scraping and rules">
  Metrics stores and queries; it does not scrape or evaluate rules. Keep Prometheus in agent mode, or Alloy, as the scraper, and evaluate recording and alerting rules with a ruler that queries the reader URL.
