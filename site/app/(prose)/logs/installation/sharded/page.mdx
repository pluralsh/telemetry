## How it works

Each writer holds the Lease on one storage shard. A entry routes to a shard by a hash of its namespace and stream labels, under the [routing epoch](/sharding/) in effect at its timestamp, and any writer accepts any entry and forwards it to the shard's owner. Each shard gets its own reader group, and a query fans out to every group and merges the results. Adding writers schedules a new epoch: new shards take data from the next aligned hour, and old data never moves.

## Scaling

- **Writers:** raise `spec.writer.replicas`. See [scaling](/logs/scaling/) for how many writers your peak rate needs and how to size each one. New pods start first, and the new shards take writes from the next aligned hour. Existing data stays where it is, so scale-down is blocked until it expires.
- **Readers:** `spec.reader.replicas` sets the replicas per reader group. Change it at any time, or set `spec.reader.autoscaling` to scale each group on CPU. New groups appear as writers add shards. See [reader groups](/sharding/#reader-groups).
- **Heavy queries:** raise `request.queryConcurrency` and `request.maxInFlightQueryBytes` together with reader memory.
